# Cluster security review — 2026-10-23

## Confirmed findings

- Trivy had only two VulnerabilityReports across 457 running pods. Five completed scan jobs occupied all scan slots: three produced oversized reports rejected by etcd/API limits, and two had unavailable container logs that appeared as base64 parsing errors. A one-hour completed-job TTL is configured and the five stuck jobs were given the same TTL. Scans resumed. This prevents indefinite queue blockage; it does **not** solve storage of oversized reports or prove complete coverage. Existing scan settings omit unfixed vulnerabilities and low severity findings.
- The four existing Kyverno policies were Audit/Ignore. An invalid Helm hook label selector prevented policy updates. That selector is removed. A separate enforced, fail-closed policy now rejects privileged containers, host namespaces and hostPath in the FreshRSS, Wallabag, Monica and MISP namespaces. Existing FreshRSS/MISP/Wallabag controller templates passed admission dry runs. Other namespaces remain audit-only.
- CrowdSec had no active remediation bouncer registered (only old dashboard consumers). Its configured acquisition covers NGINX, not the Envoy gateway now handling many routes. Detection and blocking need an Envoy integration plus end-to-end tests. A running CrowdSec pod is not evidence that requests are blocked.
- Falco runs on amd64 nodes only; the ARM64 node is outside its current coverage. One other node was NotReady. Runtime coverage needs remediation and alerting.
- Many application namespaces lack NetworkPolicies, and several policies permit all egress. Internal DNS names on a shared gateway are not access controls. Private-address restrictions were applied to both public and internal PHP routes as exposure reduction. Upstream proxy/NAT source preservation and denial from an independent WAN client are not yet verified; these restrictions do not replace patching or protect against compromised private-network clients.

## eMudhra trust-store incident

Sampled system CA bundles in FreshRSS, MISP, brain-mcp, graph embeddings, Pages, Meerkat MCP and Argo CD included emSign ECC Root CA - G3 before upgrades. This is an outbound client trust risk even when inbound website certificates use Let's Encrypt. The sample is not a full inventory of OS, Python certifi, Java, Node or embedded Go trust stores. Rebuild/redeploy affected images with updated CA bundles and verify every effective trust store; do not disable certificate verification. Node trust stores also require assessment. No compromise or absence of compromise has been established by this review.

## Deployment and next steps

Upgrade manifests and containment controls were developed on `codex/cluster-security-20261023` and integrated with the latest `main` for deployment. Application source revisions remain on `main`: the app-of-apps controller resets temporary branch overrides. The pinned MISP core image also needs a narrow startup workaround to restore the missing executable bit on `/init_misp.sh`; the upstream file-mode fix is [MISP/misp-docker#479](https://github.com/MISP/misp-docker/pull/479).

Priorities remaining: patched Wallabag image and compatibility test; exhaustive trust-store remediation; Envoy CrowdSec/AppSec blocking with client-IP validation; scan coverage/staleness/queue alerts and durable storage for oversized reports; tighter network egress and admission controls with workload-specific exceptions; ARM64 runtime detection; review high/critical scan findings against current running images. This is a targeted review and containment pass, not a declaration that the cluster is secure.

Sources: [PHP advisories](https://www.php.net/archive/2026.php), [Google eMudhra advisory](https://blog.google/security/protecting-chrome-and-android-users-from-compromised-emudhra-intermediate-ca-certificates/), [Wallabag release discussion](https://github.com/wallabag/docker/issues/480).
